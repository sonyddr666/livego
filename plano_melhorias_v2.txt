A1. TIMEOUT 1011 — BUSCA DUAL (GOOGLE NATIVO + GHOST EM BACKGROUND)
────────────────────────────────────────────────────────────────────────────────

PROBLEMA ORIGINAL:
  O Ghost Search demora 36-43 segundos. O Gemini Live API tem timeout
  interno de ~15-30s para tool calls. Quando a resposta do ghost_search
  chega, o WebSocket já foi fechado pelo Google (erro 1011).

VISÃO DO DESENVOLVEDOR:
  O Ghost Search NÃO pode ser cancelado — os dados VÃO chegar eventualmente.
  A solução é usar uma estratégia DUAL:
  
  1. Quando o Gemini pede ghost_search, INICIAR a busca em background
  2. IMEDIATAMENTE responder ao Gemini dizendo "estou buscando, enquanto
     isso vou usar o Google nativo para dar uma resposta rápida"
  3. O Gemini usa o Google Search nativo (que já está configurado como
     tool: { googleSearch: {} }) para dar uma resposta rápida
  4. Quando o Ghost Search terminar:
     a) Se a sessão ainda estiver ativa: oferecer o resultado complementar
     b) Se a sessão caiu: salvar o resultado no histórico para a próxima
        reconexão

ONDE PRECISA MUDAR:

  Arquivo: useLiveAPI.ts, Linhas 512-552 (bloco de tool calls)
  
  FLUXO ATUAL (problemático):
    1. Recebe functionCall ghost_search
    2. await handleToolCall(call)  ← BLOQUEIA 36s esperando
    3. session.sendToolResponse()  ← WebSocket já morreu = erro
  
  FLUXO PROPOSTO:
    1. Recebe functionCall ghost_search
    2. INICIA handleToolCall(call) em background (sem await)
    3. IMEDIATAMENTE envia sendToolResponse com:
       {
         ok: true,
         status: "searching",
         message: "Busca profunda iniciada. Enquanto aguardo o resultado
                   completo, posso usar minha busca nativa do Google para
                   te dar uma resposta rápida. Quer que eu pesquise agora
                   pelo Google enquanto esperamos o Ghost Search?"
       }
    4. Quando ghost_search resolver:
       a) Se isConnectedRef.current === true:
          - Armazena resultado em uma ref/state (ex: pendingGhostResults)
          - Na próxima interação do usuário, o Gemini pode ser informado
            do resultado via system prompt atualizado ou via novo tool call
       b) Se isConnectedRef.current === false:
          - Salva resultado no localStorage como parte do histórico
          - Na próxima reconexão, esse dado é carregado como contexto

  DETALHES TÉCNICOS:
  
  No useLiveAPI.ts, o bloco de tool calls (linhas 512-552) ficaria assim
  conceitualmente:
  
    // Para ghost_search: resposta imediata + busca em background
    if (call.name === 'ghost_search') {
      // 1. Responder IMEDIATAMENTE ao Gemini (evita timeout)
      const immediateResponse = {
        ok: true,
        status: 'searching_in_background',
        message: 'Busca profunda do Ghost Search foi iniciada em background.
                  Enquanto aguardo, posso pesquisar rapidamente pelo Google.
                  Pergunte ao usuário se ele quer a resposta rápida do Google
                  enquanto esperamos.',
      };
      session.sendToolResponse({
        functionResponses: [{
          id: call.id, name: call.name, response: immediateResponse
        }]
      });
      
      // 2. Busca continua em background
      handleToolCall(call).then(ghostResult => {
        if (isConnectedRef.current) {
          // Sessão ainda ativa — guardar resultado para complementar
          pendingGhostResultsRef.current.push(ghostResult);
        } else {
          // Sessão caiu — salvar no histórico para a próxima reconexão
          saveGhostResultToHistory(ghostResult, call.args.query);
        }
      });
      
      return; // Não esperar o ghost_search terminar
    }
    
    // Para outras tools: fluxo normal com await
    const result = await handleToolCall(call);
    session.sendToolResponse(...);

  NOVA REF NECESSARIA:
    const pendingGhostResultsRef = useRef<any[]>([]);

  NOVA FUNÇÃO NECESSÁRIA (em dataFunctions.ts ou no próprio hook):
    function saveGhostResultToHistory(result, query) {
      // Salva em localStorage como "resultado pendente"
      // para ser injetado na próxima reconexão
    }

A2. ÁUDIO CONTINUA ENVIANDO APÓS WEBSOCKET FECHAR
────────────────────────────────────────────────────────────────────────────────

PROBLEMA:
  O AudioWorkletNode continua enviando chunks de PCM mesmo depois do
  WebSocket fechar, gerando dezenas de erros "WebSocket is already in
  CLOSING or CLOSED state" por segundo.

CAUSA NO CÓDIGO:
  useLiveAPI.ts, Linhas 370-394: sendAudioChunk()
  - Linha 372: Verifica isConnectedRef.current
  - Linha 390: sessionPromise.then() — a promise já está resolved, então
    executa imediatamente
  - PROBLEMA: isConnectedRef.current é setado false APENAS no disconnect()
    que é chamado DEPOIS do onclose. Os chunks continuam no intervalo.

  useLiveAPI.ts, Linha 406-408: port.onmessage do AudioWorkletNode
  - Continua disparando a cada ~2.6ms (buffer 128 samples @ 48kHz)

O QUE CORRIGIR:
  1. No callback onclose (linha 557), ANTES de chamar disconnect():
     - Setar isConnectedRef.current = false IMEDIATAMENTE
     - Desconectar o AudioWorkletNode.port.onmessage = null
  2. No sendAudioChunk, adicionar try/catch no session.sendRealtimeInput()
     para capturar erros silenciosamente se o WebSocket está fechado
  3. O disconnect() já limpa o AudioWorkletNode, mas é chamado DEPOIS —
     o gap de tempo entre onclose e disconnect é onde o spam acontece

A3. GHOST SEARCH NÃO DEVE SER ABORTADO
────────────────────────────────────────────────────────────────────────────────

DIRETRIZ DO DESENVOLVEDOR:
  "Os dados da busca VÃO VIR, não importa — pode demorar mas o Ghost
  vai responder."

SITUAÇÃO ATUAL NO CÓDIGO:
  dataFunctions.ts, Linhas 594-595:
    const controller = new AbortController();
    setTimeout(() => controller.abort("Nova busca iniciada ou limite de
    tempo excedido"), GHOST_TIMEOUT_MS);
  
  O timeout é de 60s (GHOST_TIMEOUT_MS = 60000). Isso é aceitável para
  um limite de segurança, mas a mensagem "Nova busca iniciada" é
  confusa — não indica nova busca, indica timeout.

O QUE VERIFICAR/AJUSTAR:
  1. A mensagem do abort deve ser clara: "Timeout de segurança: 60s"
  2. Se o Ghost Search realmente SEMPRE responde, podemos aumentar o
     timeout ou removê-lo (mas manter um limite muito alto como 120s
     como segurança)
  3. NÃO cancelar a busca quando uma nova busca chega — cada busca
     é independente e deve completar
  4. O AbortController ATUAL já é local por chamada (um por invocação
     de ghostSearch), então não há compartilhamento. Está correto.
  5. A questão observada nos logs ("Error: Nova busca iniciada ou limite
     de tempo excedido") parece ter vindo de uma VERSÃO ANTERIOR do
     código que tinha um controller GLOBAL. Se o código atual é o da
     linha 594, isso não deveria acontecer em <60s. VERIFICAR se não
     há outro lugar que dispara abort externamente.

C1. ERRO 1008 POR RECONEXÃO SEM CLEANUP
────────────────────────────────────────────────────────────────────────────────

PROBLEMA:
  Erro 1008 "Requested entity was not found" aparece quando:
  - O frontend reconecta rápido demais após uma desconexão
  - A sessão anterior não foi completamente limpa no servidor do Google
  
IMPORTANTE (Diretriz do desenvolvedor):
  NÃO resolver removendo inputAudioTranscription ou outputAudioTranscription.
  Essas configs são ESSENCIAIS para a transcrição ao vivo (legendas).

CAUSA PROVÁVEL:
  useLiveAPI.ts:
  - Linha 147-151: disconnect() faz session.close() via .then() (async)
    e imediatamente seta sessionPromiseRef = null
  - Se o usuário clica em reconectar antes do session.close() completar,
    duas sessões podem coexistir momentaneamente
  - O servidor Google pode rejeitar a nova conexão com 1008

O QUE CORRIGIR:
  1. Adicionar cooldown mínimo entre disconnect e novo connect:
     - Após disconnect(), esperar 1-2s antes de permitir novo connect
     - Ou melhor: disconnect retorna Promise que resolve quando cleanup
       está completo
  2. Garantir que session.close() complete ANTES de permitir reconexão:
     - Converter o .then() para await
     - Ou usar flag "isCleaningUp" que bloqueia novo connect
  3. Melhorar mensagem de diagnóstico no onclose:
     - 1008 na Live API = "Sessão anterior não foi limpa corretamente"
     - NÃO "API key inválida" (mensagem atual é enganosa)

VERIFICAÇÃO DO CÓDIGO DE HISTÓRICO — ANÁLISE DETALHADA
================================================================================

O desenvolvedor pediu para verificar se o save/get histórico está
"normal e regulado". Aqui está a análise:

── SAVE HISTÓRICO ──

  LOCALIZAÇÃO: App.tsx, Linhas 118-138 (handleEndCall)
  
  FLUXO:
    1. Calcula duração (endTime - startTimeRef.current)
    2. Verifica se transcript.trim().length > 0
    3. Cria HistoryItem: { id, date, duration, transcript }
    4. setHistory(prev => [newItem, ...prev])  ← prepend (mais recente 1º)
    5. useEffect[history] persiste no localStorage
    6. Chama disconnect()
    7. Volta para HomeScreen

  PROBLEMAS ENCONTRADOS:
  
    a) SÓ SALVA EM AÇÃO MANUAL: handleEndCall só é chamado pelo botão
       "encerrar". Se a conexão cair, NADA é salvo. (Ver B1)
    
    b) NÃO INCLUI TOOL RESULTS: O histórico salva APENAS o transcript
       de áudio. Resultados de ghost_search, fetch_page, show_image
       são ignorados. (Ver B2)
    
    c) ORDEM: disconnect() é chamado DEPOIS de setHistory. Como
       setHistory é assíncrono (useState), a persistência no localStorage
       via useEffect pode não ter executado quando disconnect() limpa
       tudo. Na prática, React batcha os updates, então geralmente
       funciona, mas não é garantido.
    
    d) DATE FORMAT: Usa new Date().toLocaleString(locale), que gera
       formato "16/01/2026, 23:08:13" em pt-BR. Na dataFunctions.ts,
       parseBrazilianDate() parseia esse formato. FUNCIONA, mas é
       frágil — muda se o locale mudar.

── GET HISTÓRICO ──

  LOCALIZAÇÃO: App.tsx, Linhas 48-56 (useState initial value)
  
  FLUXO:

  PROBLEMAS ENCONTRADOS:
  
    a) CAMPOS OPCIONAIS NÃO EXISTEM: parseHistoryToEntries espera
       item.emotion e item.intensity (linhas 316-317), mas o
       HistoryItem criado no App.tsx NÃO tem esses campos:
       
       App.tsx cria:  { id, date, duration, transcript }
       Parser espera: { id, date, duration, transcript, emotion, intensity }
       
       Resultado: emotion = undefined, intensity = undefined
       IMPACTO: Filtros por emoção e estatísticas emocionais NUNCA

       apenas com notas emocionais salvas separadamente.

       do mesmo localStorage key ('livego_history'), mas com parsers
       diferentes. Se o formato mudar em um, o outro quebra.
    
    c) LIMIT DE 10: getConversationHistory retorna .slice(0, 10) —
       no máximo 10 conversas. Se o usuário tiver centenas, o Gemini
       só vê as 10 mais recentes filtradas.
    
    d) NO SEARCH RESULTS IN HISTORY: Quando o Gemini chama 
       getConversationHistory ou searchConversationTopic, os resultados
       NÃO incluem dados de buscas que foram feitas nas conversas.
       Apenas o transcript de áudio é pesquisável.
