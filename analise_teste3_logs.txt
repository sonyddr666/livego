4. ⚠️ SPAM DE ÁUDIO — try/catch NÃO RESOLVE
────────────────────────────────────────────────────────────────────────────────

  EVIDÊNCIA:
  Mesmo com try/catch no sendAudioChunk, os erros CONTINUAM:
  
  useLiveAPI.ts:428 WebSocket is already in CLOSING or CLOSED state.
  × 8 vezes (sessão 1) e × 7 vezes (sessão 2)

  POR QUE O try/catch NÃO PEGA:
  
  O erro "WebSocket is already in CLOSING or CLOSED state" é um 
  ERRO DO BROWSER, não uma exceção JavaScript.
  
  Quando você chama WebSocket.send() em um WS no estado CLOSING:
  1. O BROWSER loga "WebSocket is already in CLOSING or CLOSED state"
     no console (erro nativo, não capturável por JS)
  2. A chamada NÃO lança exceção em JavaScript
  3. O try/catch não tem nada para pegar
  
  É como se o Chrome fizesse um console.error() interno antes de
  retornar. Não há como capturar isso com código JavaScript.
  
  O caminho real é EVITAR chamar ws.send():
  
  SOLUÇÃO REAL:
  O problema é que isConnectedRef.current ainda é TRUE quando o WS
  entra em CLOSING. A flag só muda para FALSE no onclose. O gap é:
  
  [WS abre] → [algo faz WS entrar em CLOSING] → 
  → [~8 chunks] → [onclose dispara] → isConnectedRef = false
  
  Para eliminar 100%, precisamos:
  1. Antes de session.sendRealtimeInput(), verificar o estado REAL
     do WebSocket: session.ws?.readyState === WebSocket.OPEN
  2. OU: a SDK do Google GenAI não expõe o WS diretamente, então
     precisamos interceptar de outra forma
  3. OU: aceitar que são erros cosméticos do browser (não afetam
     funcionalidade, são apenas logs vermelhos no console)
  
  NOTA IMPORTANTE: Esses erros NÃO causam crash, NÃO afetam
  a funcionalidade. São puramente cosméticos no DevTools. O app
  continua funcionando perfeitamente.

  IMPORTANTE: Nas sessões 1 e 2, NENHUMA mensagem foi trocada.
  O WebSocket abriu, o áudio pipeline foi montado, e IMEDIATAMENTE
  o servidor fechou com 1008. Não houve tool call, não houve fala,
  não houve nada.
  
  CAUSAS PROVÁVEIS:
  
  a) CONTEXTO DA SESSÃO ANTERIOR MUITO GRANDE:
     As sessões 1 e 2 tentaram restaurar contexto de dropped sessions
     anteriores (App.tsx:205 "Restoring context from dropped session...")
     Se o transcript + toolResults da sessão anterior era muito grande,
     a system instruction pode ter excedido algum limite do Gemini.
     
     Na sessão 3, o contexto pode ter sido menor (ou a sessão 1 e 2
     não tinham transcript, apenas toolResults vazios).
  
  b) RECONEXÃO RÁPIDA DEMAIS:
     Sessão 1 fecha → imediatamente reconecta → Sessão 2
     Sessão 2 fecha → imediatamente reconecta → Sessão 3
     
     A sessão anterior pode não ter sido limpa no servidor do Google
     quando a nova conexão é aberta. No servidor, a sessão velha 
     ainda está "morrendo" quando a nova tenta usar seus recursos.
  
  c) "Operation is not implemented, or supported, or enabled":
     Este erro (sessão 1) sugere que alguma CONFIGURAÇÃO enviada na
     sessão não é suportada. Possibilidades:
     - inputAudioTranscription com contexto muito grande
     - Algum parâmetro do config que o servidor não aceita
     - A combinação de tools + googleSearch + transcription pode
       ter alguma limitação

  d) TRANSIENTE:
     O Gemini Live API é relativamente novo e pode ter issues
     transientes. O fato de que a sessão 3 funciona com a MESMA
     config sugere que pode ser race condition do lado do Google.

  O QUE PRECISA SER FEITO:
  1. Adicionar DELAY (ex: 2 segundos) entre uma desconexão e a 
     próxima tentativa de conexão para dar tempo ao servidor de
     limpar a sessão anterior
  2. Limitar o tamanho do contexto injetado da dropped session
     (ex: máximo 2000 caracteres de transcript)
  3. Detectar 1008 e NÃO reconectar automaticamente no loop —
     esperar a ação manual do usuário
